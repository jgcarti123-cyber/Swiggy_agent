# CLAUDE.md

## Project

A personal, single-user, local-only web dashboard built on the official Swiggy Builders Club MCP servers. One page, a sidebar, two panels:

1. **Feast Finder** (food dish compare) — type a dish, see nearby open restaurants that serve it, ranked by rating (distance as tiebreak), with a veg/non-veg/all filter, up to 6 matching items per restaurant with photos and LLM-estimated nutrition, and an on-demand real coupon price per item.
2. **Pantry Pal** (Instamart order chat) — a chat box where free-text messages ("add milk") are turned into Instamart search/cart/checkout actions, with a live cart panel that always reflects the real cart state. Broad requests get a guided brand → variant picker (with photos and a quantity stepper); most of that flow is **deterministic, not LLM-driven** — see "Pantry Pal's real architecture" below before touching it.

Runs on `localhost` only. Single user (the account owner). No multi-tenant auth, no public deployment, no Telegram bot, no Dineout — those are separate projects and explicitly out of scope here.

For the full "why is the code shaped this way" narrative — every verified Swiggy tool quirk, every Groq rate-limit incident, the full Pantry Pal architecture with measured before/after numbers — see **`ARCHITECTURE.md`**. This file is the quick-reference brief; that one is the detailed record.

## Absolute rule: no hallucinated Swiggy tools or parameters

Before implementing any call to a Swiggy MCP tool, fetch and read the corresponding doc below. Never invent a tool name, parameter, error code, or auth detail. If a doc doesn't cover something you need, stop and ask rather than guessing — Swiggy's own agent-authoring guidance is explicit about this.

This isn't theoretical: several things in the docs below turned out not to match the live server (see the "Verified to NOT work as documented" callouts) — they were only caught because the actual tool responses were inspected live, not assumed from the doc text. Docs describe intended behavior; the running server is the source of truth.

## Tools this project actually calls (fetch each `.md` before touching)

**Food** — all called from `backend/src/mcp/foodClient.js`:
- `get_addresses` — https://mcp.swiggy.com/builders/docs/reference/food/get_addresses.md
- `search_restaurants` — https://mcp.swiggy.com/builders/docs/reference/food/search_restaurants.md — restaurant/cuisine **name** search, not dish search. This is the real entry point for Feast Finder (see below), not `search_menu` unscoped.
- `search_menu` — https://mcp.swiggy.com/builders/docs/reference/food/search_menu.md — dish-level search, called **scoped** (`restaurantIdOfAddedItem` set) per candidate restaurant. **Verified to NOT work as documented when called unscoped**: the doc describes omitting `restaurantIdOfAddedItem` as searching across restaurants near an address — live testing across many dishes/addresses on the current beta returns zero results every time. Do not build around unscoped `search_menu`; it doesn't work right now, however the doc reads. `vegFilter` on this tool only supports veg-only (`1`) or mixed (`0`/omitted) — there is no non-veg-only value.
- `get_restaurant_menu` — https://mcp.swiggy.com/builders/docs/reference/food/get_restaurant_menu.md — unused in the current flow (kept as a typed wrapper); has a real Swiggy-authored `description` field that `search_menu` items lack, if nutrition/allergen text is ever wired in properly.
- `fetch_food_coupons` / `apply_food_coupon` — https://mcp.swiggy.com/builders/docs/reference/food/fetch_food_coupons.md — **Verified to NOT work as documented**: `fetch_food_coupons` returns a bare `{}` regardless of cart/coupon state on the live beta, so it cannot be used for parallel no-cart price estimation as originally planned. The only way to see a real coupon price is to build an actual cart and read the auto-applied offer (see `couponCheck.js`), then `apply_food_coupon` it explicitly (auto-suggestion alone reports `discount: 0` until applied).
- `update_food_cart`, `get_food_cart`, `place_food_order`, `track_food_order`, `flush_food_cart`, `report_error` — used as documented, all cart-touching ones gated behind an explicit user click.

**Instamart** — all called from `backend/src/mcp/instamartClient.js`:
- `get_addresses` — used only by the `/api/instamart/addresses` route (the address picker UI), never by the chat agent.
- `search_products` — returns `products[]`, each with `brand` and a `variations[]` array (`spinId`, `skuId`, `quantityDescription`, `price.mrp`/`price.offerPrice`, `imageUrl`, `isInStockAndAvailable`). Confirmed live: Swiggy freely mixes out-of-stock variants into results with no separate flag needed beyond `isInStockAndAvailable` — the app must not assume everything returned is buyable.
- `update_cart` — https://mcp.swiggy.com/builders/docs/reference/instamart/update_cart.md — **replaces the entire cart**, not additive; every caller reads `get_cart` first and sends back the full merged list. Also confirmed live: rejects an **empty** items array outright ("items array is required and must contain at least one item") — removing the last item in the cart has to go through `clear_cart` instead, never `update_cart` with `items: []`.
- `get_cart` — returns `items[]` (with `spinId`, `skuId`, `itemName`, `quantity`, `mrp`, `discountedFinalPrice`, `imageUrl`), `cartTotalAmount`, `billBreakdown`, plus a large `selectedAddressDetails` block the app doesn't need. When there's no active cart it throws a tool error ("Cart not found or session expired...") rather than returning an empty list — treated as a normal empty cart everywhere in this app, not surfaced as an error.
- `clear_cart` — idempotent in effect; used both for the "Clear cart" action and as the fallback when a mutation would otherwise leave `items: []`.
- `your_go_to_items` — same `products[]`/`variations[]` shape as `search_products`. **Read-only** (there is no Swiggy tool to edit this list). Used as the "most ordered by you" signal cross-referenced into every guided search (see Pantry Pal section below). It is **not** what backs the "Reorder my usuals" button anymore — that's now a local, user-editable list (see below), precisely because `your_go_to_items` can't be edited.
- `checkout`, `get_payment_options` — only reachable after explicit user confirmation in chat; never retried automatically (see Pantry Pal section below — retrying a payment call could double-order).
- `get_orders`, `get_order_details`, `track_order`, `create_address`, `delete_address`, `report_error` — see the reference index; not currently wired into either feature. **Note:** there is no `get_delivery_status` tool — an earlier version of `instamartClient.js` called that name and it never matched a real Instamart tool (confirmed against the live reference index: the real tool is `track_order`, already wrapped separately as `trackOrder`); the bogus wrapper was unused and has been removed.

## Auth

OAuth 2.1 + PKCE with phone + OTP in the browser, per https://mcp.swiggy.com/builders/docs/start/authenticate.md. Dynamic Client Registration (RFC 7591) means there's no client_id to apply for manually during local dev — the MCP client library handles it. Access tokens last 5 days; **there is no refresh token in v1** — treat every 401 as "re-run the authorization flow," not as a bug to patch around. Store the token server-side only, never in frontend code or browser storage. Build against `http://localhost` redirect URIs first — no approval needed for this stage; production access is a separate, later step (see Access & onboarding doc above).

Separately from token expiry: the backend keeps one cached, connected MCP client per server URL for the life of the process. That connection itself can go stale independently of the token (confirmed live — a long-running cached connection kept failing with a raw "fetch failed" network error while a brand-new connection to the identical server succeeded instantly). `mcpClient.js` now drops the cached connection on network-level failures, not just 401s, so the next call reconnects instead of repeating the same dead connection's failure.

**Every tool response can arrive wrapped in Swiggy's documented `{success, data, message}` envelope, or unwrapped — inconsistently, not as a clean migration.** This project's docs always described that envelope, but live testing for most of this project's history found the real payload arriving flat (`raw.products`, `cart.items` directly). Confirmed live in a later session that this is no longer reliable: `get_cart` for an empty cart returned the full wrapped object instead of throwing, and a "banana chips" search had 20 real results sitting under `raw.data.products` while the app checked `raw.products` and reported a false "couldn't find anything" — repeated calls showed it isn't constant either. Fixed once, at the source: `mcpClient.js`'s `extractResult`/`unwrapEnvelope` now normalizes both shapes before any caller ever sees the result, so `foodClient.js`/`instamartClient.js` and everything built on them can keep assuming a flat shape. If you're adding a new Swiggy tool call, you don't need to think about this — it's already handled at the chokepoint — but if a response ever looks wrong, check whether it's actually the wrapped envelope before assuming something else is broken.

## Feature 1: Feast Finder

Real flow (do **not** rebuild around unscoped `search_menu` — see above, it doesn't work):

1. `search_restaurants(dish)` → filter to `availabilityStatus: "OPEN"`. If zero results, ask an LLM to normalize spelling and retry once.
2. If still zero, ask an LLM for **broader** search terms (base dish with qualifiers stripped, cuisine, category — never narrower) and re-search with each in parallel; only terms that actually returned restaurants become "try instead" chips shown to the user.
3. One bounded LLM call picks up to 10 plausible candidate restaurants from name + cuisine tags.
4. Scoped `search_menu(dish, restaurantId)` per candidate, in parallel (4 at a time) — `vegFilter: 1` when the user's filter is "veg" (native, cheaper); "nonveg" and "all" fetch mixed results, with "nonveg" filtered client-side (`!item.isVeg && !item.veg`) since the tool has no non-veg-only mode.
5. One bounded LLM call judges, across all restaurants' surviving items at once, which are *genuinely* the requested dish (real food knowledge, not keyword matching — needed because scoped `search_menu` falls back to loosely-related items instead of an empty list when a restaurant has no real match).
6. Sort each restaurant's surviving items by rating, keep top 6.
7. One bounded LLM call estimates protein/kcal for the final displayed item set — **a guess from the dish name, not real data**; Swiggy's tools have no nutrition field. Label it as an estimate in the UI.
8. Sort restaurants by rating desc, distance asc. Only touch the cart (`update_food_cart`, `apply_food_coupon`) once the user clicks to actually order.

Also on the Feast Finder screen: a veg/non-veg/all pill toggle, and a "surprise me" dice button that fills the search box from a curated, veg/nonveg-tagged dish list (`frontend/src/data/dishes.js`) respecting the active filter — client-side only, no backend call.

## Feature 2: Pantry Pal

**Read this before changing anything in `backend/src/agent/instamartAgent.js`.** The chat agent is deliberately **not** a pure "every message goes to the LLM, which decides everything" loop anymore — it was, and it was unusably slow (measured 7 Groq completions / ~129s for one guided add). Most of the guided-search and cart-mutation flow is now **deterministic code**, not model judgment:

- **Off-topic guardrail — two layers, so random questions never get answered and don't burn tokens.** Pantry Pal used to happily answer "what is the capital of india?" (one wasted Groq completion per random question). Now: (1) a **zero-Groq-call deterministic pre-gate** (`looksOffTopic` in `sendMessage`, before the LLM loop) refuses obvious non-grocery messages instantly — high-precision by design (only fires when confident, so it can **never** block a real grocery request; anything with a shopping signal or that's ambiguous passes straight through), and (2) the **`SYSTEM_PROMPT` has a hard "refuse anything non-grocery" rule** as the backstop for whatever the pre-gate misses (that still costs one small refusal completion, but the model never actually answers). Verified: capitals/weather/math/coding/chit-chat all refused; "add milk", "what milk do you have", "i need stuff for breakfast" all still pass through. If you add off-topic patterns, keep them gated behind interrogatives/task-verbs so plain product names never trip them.
- `search_products` is the only thing the model calls to find products. What happens next — ask which brand (only when 2+ brands are found, each option **verified to have an in-stock variant**), or show variants (sorted in-stock-first, then price ascending, in a code-decided branch, not a second model completion) — is decided in `runSearchAndBranch()` immediately after the search runs, via a `__endLoop` sentinel `executeTool` can return to end the tool loop without another completion.
- Naming a previously-offered brand, picking the "Any brand" option, clicking "Add" on a product card, "Show more", "Reorder my usuals", "Clear cart", saving/removing a usual (☆ / ×), the daily-schedule toggle, and the cart's +/- quantity stepper are **all zero-LLM direct actions** (`addItemDirect`, `showMoreDirect`, `clearCartDirect`, `reorderUsualsDirect`, `saveUsualDirect`, `removeUsualDirect`, `setItemQuantity`) — plain `get_cart` → merge → `update_cart` (or local DB writes) in code. The model is only ever invoked to turn genuinely free-text requests into a search query, or to handle free-text cart/usuals edits ("remove the bread") that need real reasoning about current contents.
- The delivery address is resolved server-side from the saved address and injected into every tool call — the model never sees or asks for one. `get_addresses`/`get_orders`/`track_order` are not in the model's tool list at all.
- Product photos never reach the model (stripped for tokens) — a server-side cache keyed by `spinId` holds the full variant data from search results, and card-rendering joins photos/prices back by id. `get_cart` already returns `imageUrl` per line item directly, so the cart doesn't need this cache.
- `update_cart`/`clear_cart` retry once automatically on failure (both idempotent — replaying the same payload is safe) and drop the cached MCP connection on a network-level failure first (see Auth section) so the retry gets a fresh connection. **Never add this kind of automatic retry to `checkout`/`confirm_order`** — those aren't idempotent, and retrying one blindly could create a duplicate order.
- Some Instamart items report as fully in-stock in search yet still get rejected by `update_cart` unpredictably (confirmed live, not something the search response can predict) — these fail with a short actionable message, never a raw multi-line dump, and never cascade into blocking the next add.
- **"Most ordered by you"**: every `search_products` call in `runSearchAndBranch()` also fetches (cached 5 min per address, invalidated on checkout) `your_go_to_items` in parallel and cross-references the results by `spinId` (exact) or `brand`+`displayName` (fallback, different pack size of the same regular purchase). A match gets sorted to the front and, on product cards, sets the existing `note` field to `"(Most ordered by you)"` (the frontend already renders `product.note`, so no UI change was needed); on the brand-choice screen the matched brand is moved first and its **displayed label only** gets the suffix — the underlying `brandsOffered` list used for matching stays the clean brand name, never the annotated one. This is Swiggy's own live data, not a local order log — see ARCHITECTURE.md §6.9 for why.
- **Search relevance**: `search_products` falls back to loosely/semantically related items instead of empty results, same as `search_menu` on the Food side (confirmed live: searching "chicken" returned "Too Yumm Protein Chips," no relation at all, alongside real chicken items). Fixed with a deterministic keyword filter (`filterRelevantProducts`) — a product survives only if one of the query's own significant words appears in its name or brand — not a second LLM judgment call, to avoid reintroducing the latency this section already removed once. This can't tell "chicken breast" from "chicken masala" (both literally say chicken); see ARCHITECTURE.md §6.10 for the full trade-off. `tokenVariants`'s plural folding strips both trailing "s" and "es" ("tomatoes"→"tomato") — the "s"-only version left "tomatoes" unmatched against "Tomato" product names, which fell through the whole filter and silently auto-added a carrot instead (confirmed live, now fixed). **Proportional safety valve**: the filter also keeps the *unfiltered* set when only a small fraction (<25%, on 8+ results) literally match — that's the signature of a category/synonym query the keyword filter can't handle ("underwear" returns 20 real products but only 1 literally says "underwear"; the rest are "trunk"/"brief"/"boxer", so filtering to that 1 dropped 19 relevant items — confirmed live as the underwear-vs-underpants gap). Food noise is unaffected: for "chicken" most results *do* contain "chicken" (well above the threshold), so the noise is still removed.
- **Instamart is a general store, not just groceries — the scope guardrail must not refuse apparel/personal-care/etc.** The off-topic guardrail's system-prompt scope originally said "grocery shopping", and the model started refusing "add underwear" as non-grocery. Fixed: the SCOPE rule now says Instamart sells groceries **and** household, personal/baby care, apparel/innerwear, stationery, electronics, pet supplies, etc. — search for any plausible product, only refuse genuinely non-shopping questions (trivia/math/coding/chit-chat). The deterministic pre-gate (`looksOffTopic`) already passes anything with a shopping verb like "add", so this was purely the model over-narrowing "grocery".
- **Recipe/import "best pick" is NOT the cheapest of Swiggy's raw order, and NOT always the cheapest of the 3 shown either**: `sortForBestPick` (§6.10-adjacent, used only by the recipe/import auto-add paths) keeps mostOrdered-first but otherwise trusts Swiggy's own relevance order instead of re-sorting by price — confirmed live this was a real bug (a ₹46 "Suhana Chicken Masala" was jumping ahead of ₹150-290 real chicken cuts that Swiggy itself ranked higher). On top of that, `orderBestFirst` decides which of the top-3 *relevant* options actually gets auto-added: a "most ordered by you" match wins even if pricier (stronger personal signal), otherwise the cheapest of the 3. The guided browse/choose picker (§6.4/§6.5) is untouched — still cheapest-first, since there the user is comparing options themselves.
- **Recipe ingredient wording uses Indian grocery terms, not US ones**: the `propose_ingredients` system-prompt instruction now says "curd" not "yogurt" (confirmed live: "yogurt" surfaces sweetened Greek/flavoured tubs, "curd" returns plain dahi), plus "coriander leaves"/"capsicum"/"paneer" over their US-English equivalents — otherwise the model's own ingredient list would search for the wrong category of product on an Indian catalogue.
- **Requested-quantity filter**: if the query states a pack size ("100g paneer", "1kg rice", "2 pieces chicken" — the system prompt tells the model to keep this verbatim), `filterByRequestedQuantity` narrows to variants whose own `quantityDescription` matches (parsed and compared as `{family: weight|volume|count, value}`, g/kg and ml/l normalized; a multipack like "65 g x 2" is matched on its per-pack size, not the multiplier) *before* brand grouping and sorting run — so a brand that only sells a different size is never offered as a choice, and "show more" only ever pages through the matching size. If nothing at that size exists, falls back to every size with a "couldn't find a 100 g pack — here's what's available" notice rather than a false empty result. No extra LLM call.
- **Clothing-size filter** (`filterByRequestedSize`, alongside the quantity filter): apparel sizes are a *different dimension* Swiggy encodes in the SAME `quantityDescription` as a suffix after the count ("1 L" = one, size Large; "2 XL"; "1 M x 2"). "show me only size L underpants" now shows only L. Crucially the "L" here is **Large, not litre** — `parseSizeFrom` only treats a single letter as a size when there's a clear signal (the word "size", a full size word like small/medium/large, an unambiguous XS/XL/XXL token, or an apparel word like underwear/trunk/socks), so "1 l milk" stays volume and "small onions"/"large pizza" don't get size-filtered. Same fallback-with-notice behavior as the quantity filter. The two filters are mutually exclusive per query and both run before brand grouping.
- **Explicit-brand auto-detect**: asking "which brand?" when the user already said the brand in their message (e.g. "order SuperYou 10g Protein Wafer Bar" — Swiggy's fuzzy search still fans out into Yogabar/Ritebite/etc.) is exactly the annoyance a brand question exists to resolve, not create. `detectExplicitBrand` checks, only when 2+ brands would otherwise trigger the ask, whether the query's own words contain one (and *only* one) of the candidate brand names as a contiguous token match — word-boundary, not raw substring, so a short brand name can't match part of an unrelated word. If exactly one is named, the ask is skipped and results go straight to product cards, same as answering the brand question yourself. If the query happens to name two real brands that textually overlap (e.g. "Godrej Real Good chicken" contains both "Godrej Real Good" and "Real Good Chicken"), that's genuinely ambiguous and it still asks — the detector only ever removes a question, never a real one.
- **Editable "usuals" list (local)**: "Reorder my usuals" is backed by a **local, user-editable list** in SQLite (`usuals` table), **not** Swiggy's read-only `your_go_to_items`. It starts empty. Items are saved via a ☆ on any product card (`saveUsualDirect`), removed via the My Usuals panel's × (`removeUsualDirect`) or the chat agent's `remove_from_usuals` tool (fuzzy token-match against the local list — "amul milk" matches "Amul Taaza Milky Milk"). "Reorder now" / "Reorder my usuals" merges the whole local list into the cart (`addUsualsToCart` → `addUsualsBestEffort`, which falls back to adding items one at a time if a batch fails so one out-of-stock item can't block the rest). The agent doesn't add to usuals itself — it searches so the user can ☆-save. See ARCHITECTURE.md §6.11.
- **`update_cart` can silently drop an item with no error at all** — confirmed live, distinct from the already-documented "whole batch rejected" case (§6.5): a batch `update_cart` returned success while one item (Swiggy-reported `isInStockAndAvailable: true`) never actually landed in the cart, so a reply built from "the call didn't throw" alone can falsely claim success. Both `addUsualsBestEffort` and `addItemDirect` now verify the *returned cart's actual contents* against what was requested (never trust a non-throw as proof), retry once if something's missing, and always report counts from the final real cart state. Never build an "Added ✓" / "Added N" message from call success alone — check the cart.
- **Daily auto-add scheduler**: an interval-based scheduler (`backend/src/scheduler.js`, started in `server.js`) can auto-merge the usuals list into the cart at a user-set time each day (`usuals_schedule` table). It **only adds to the cart — never checks out** (respects the "no automated checkout" non-goal; adding is reversible, ordering is not). It only runs while the backend process is up and the token is valid; a run blocked by an expired token or a backend that was down past a 10-min grace window is **flagged, not caught up** (`last_status` surfaced in the My Usuals panel). Setting a schedule primes today's run-marker so a newly-chosen time takes effect from its next occurrence, never retroactively. See ARCHITECTURE.md §6.12.
- **Import from a screenshot**: the user can upload a cart screenshot from any other quick-commerce app (a round "+" attach button on the chat input — a real SVG in the app's line-icon style, not an emoji). Picking a file **stages** it: a "Ready to send" preview strip shows the actual thumbnail with an × to cancel, and nothing uploads until the user hits Send — auto-sending on file-pick was tried and rejected, since the user should see and confirm what's being sent. The user can type a note alongside it (e.g. "only get the snacks") which is forwarded as a real instruction to the vision call, not just decorative chat text. The sent bubble then shows the actual image inline. One **vision** Groq call (`config.groqVisionModel`, default `meta-llama/llama-4-scout-17b-16e-instruct` — the default text model has no image input) reads the product line items (`extractItemsFromImage` in `backend/src/agent/imageImport.js` → `[{name, size, quantity}]`, prices/offers/delivery ignored). That renders as an **editable review checklist** (adjust quantity, remove misreads) — nothing hits the cart until the user confirms. Confirm (`/import-confirm` → `confirmImportDirect`) is then **fully deterministic**: each item runs the same search + relevance + go-to + stock pipeline as a typed order, with **strict size matching** (§6.14's `parseQuantityFrom`/`quantityMatches`) — an exact in-stock same-size match is auto-added at the screenshot's quantity (best-pick chosen by `orderBestFirst`, see above); a size-only mismatch or no match shows up to 3 alternatives to pick from (reuses the §6.13 `recipe` render + `/recipe-swap`, which now carries a `quantity`). The frontend downscales/JPEG-compresses the image before upload; `express.json` limit raised to 8mb. See ARCHITECTURE.md §6.15.
- **Recipe flow ("order things for making biryani")**: costs exactly **one Groq completion** end-to-end. The model's only job is calling `propose_ingredients(dish, ingredients[])` — the ingredient list rides in the tool-call args, ends the loop via `__endLoop`, and renders as an editable checklist (chips with ×, an add-input, Confirm). Confirm hits `/recipe-confirm` (`confirmRecipeDirect`), which is **fully deterministic**: each ingredient searched in parallel (3 concurrent, same rate-limit cap reasoning as Feast Finder), through the same relevance filter + go-to cross-ref + stock/price sort as normal guided search; the best in-stock option per ingredient is auto-added via `addUsualsBestEffort` (real-cart-verified counts — reply says "Added N of M", missing ingredients named), and up to 3 **compact** options per ingredient render with Swap buttons (small rows, not the big card grid — deliberate, so ~12 ingredients don't flood the chat). `/recipe-swap` (`swapRecipeItemDirect`) replaces that ingredient's cart line atomically (a rejected add leaves the old item in place, never half-swapped) and updates the transcript entry's "added" marker in place. The checklist entry is marked `confirmed` server-side so a reload can't double-add. See ARCHITECTURE.md §6.13.

## UI: Swiggy visual language (already implemented, not just aspirational)

The app already uses Swiggy's signature orange (`#FC8019`) as the primary accent, near-black (`#282C3F`) headings, white/light-gray card backgrounds, generously rounded corners, Poppins type, pill-shaped filter chips, a filled green rating badge, and a small muted delivery-time badge — see `frontend/src/index.css`. A sidebar (`Sidebar.jsx`) switches between the two panels; both stay mounted (`hidden` attribute) so switching tabs never loses in-progress state. An original wordmark/icon is used throughout — Swiggy's actual logo is never reproduced. When adding new UI, match this existing system rather than introducing new tokens.

Pantry Pal's chat canvas is deliberately large (wide grid column + near-viewport-height message area, scrolling internally); the My Usuals panel is collapsible (open by default — its whole header is the toggle); and the typing indicator is dots plus a rotating status line (`THINKING_LINES` in `InstamartChat.jsx`) that advances every ~2s and parks on the last line rather than looping.

## Stack

React + Vite frontend, Node/Express backend, SQLite for local state (OAuth client + token, saved address id, order history, the editable `usuals` list, and the `usuals_schedule` row for the daily auto-add). The backend is the only thing that talks to Swiggy MCP and holds the OAuth token; the frontend never calls Swiggy directly. The backend listens on `127.0.0.1` only (loopback), never `0.0.0.0` — it holds the live Swiggy token and exposes unauthenticated cart/order endpoints, so it must not be reachable from other devices on the network. A single interval-based scheduler (`scheduler.js`) also runs in the backend process for the daily usuals auto-add.

## Non-goals for this build

No Telegram bot. No multi-user support. No production Swiggy access application yet (build and test against `http://localhost` / dev only). No Dineout integration. No automated checkout without an explicit user click.
